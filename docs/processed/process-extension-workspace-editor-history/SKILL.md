## 3. 본문 기록

### 3.1. context-and-scope

- Context and Scope
- workspace/src/webviewShell.js의 Design과 View는 모두 후속 Work Unit 안내만 표시하는 placeholder다.
- workspace Webview는 TAB_DEFINITIONS에서 탭, panel, 선택 헤더와 저장 상태를 생성한다.
- 공통 문서 계약은 Intake, Specification, Work Unit을 metadata, title, table of contents, section, optional block 구조로 표준화한다.
- 공통 계약은 artifact별 required section과 manager 검증 규칙까지 동일하게 만들지는 않는다.
- Design과 View를 단일 Editor 탭으로 교체하고 네 탭 순서 및 상태 이전 구현
- 프로젝트 내부 Intake, Specification, Work Unit sectioned package 탐색 및 안전한 읽기 경계
- artifact와 section 트리, 구조화 필드 편집, 읽기 전용 JSON 미리보기
- artifact별 allowlisted manager 명령을 통한 저장, 재검증, 오류 표시
- 관련 controller, Webview message contract, 단위·통합·E2E 테스트
- Agent Factory Workspace requirements Specification 정렬
- 원시 JSON 파일 직접 쓰기
- canonical manager 또는 profile 변경
- Kanban DnD와 Action 계약 변경
- Agents 확장 또는 Web 애플리케이션 변경
- Human 승인 없는 integration, cleanup, 배포, push 또는 PR promotion

### 3.2. decisions-and-open-items

- Decisions and Open Items
- Human은 Design과 View를 manager 기반 읽기·쓰기 Editor 하나로 통합하고 artifact/section 트리, 구조화 편집, 읽기 전용 JSON 미리보기를 사용하도록 선택했다.
- INTERVIEW-FUNCTION-001
- INTERVIEW-LAYOUT-002
- Human은 Dashboard, Editor, Kanban, Context 순서를 선택했고 기존 design 또는 view 선택 상태는 editor로 이전한다.
- 실제 설치본에서 artifact 탐색, 편집, validation 오류와 상태 이전을 Human이 검토해야 한다.
- integration, cleanup, 배포, push와 PR promotion은 별도 Human 결정이다.
- 범용 편집 요청이 raw JSON 또는 임의 manager invocation으로 확장되면 canonical validation 경계를 우회할 수 있다.
- 다른 프로세스가 artifact를 갱신하면 stale edit가 최신 내용을 덮을 수 있으므로 저장 직전 identity 및 documentVersion 재검증이 필요하다.
- 기존 design 또는 view 상태를 editor로 이전하지 않으면 첫 로드가 Dashboard로 되돌아갈 수 있다.

### 3.3. evidence-and-findings

- Evidence and Findings
- Design과 View는 현재 실제 읽기 또는 편집 기능이 없는 placeholder다.
- 탭 생성, panel 생성, 선택 헤더, 키보드 탐색과 vscode state 저장은 TAB_DEFINITIONS 기반이다.
- 기존 Specification은 다섯 탭과 Design 및 View 분리를 명시하므로 정렬이 필요하다.
- 세 artifact는 공통 물리 골격을 사용하지만 각 manager와 profile은 별도다.
- 단일 Editor는 공통 읽기 모델을 공유하되 쓰기는 artifact별 manager adapter로 분리해야 한다.
- 현재 저장소에는 범용 Editor controller나 artifact manager adapter가 없다.
- Editor 탭 기능 범위 결정
- 공통 JSON 골격과 manager 검증 규칙을 함께 활용해 중복 탭을 제거한다.

### 3.4. request-and-goal

- Request and Goal
- 탭 순서는 Dashboard, Editor, Kanban, Context다.
- 저장된 design 또는 view 선택 상태는 editor로 이전된다.
- Editor는 artifact와 section 탐색 트리, 구조화 필드 편집, 읽기 전용 JSON 미리보기를 제공한다.
- Intake, Specification, Work Unit 저장은 각 artifact manager를 통해서만 수행한다.
- 기존 Kanban 동작과 접근 가능한 탭 키보드 탐색을 보존한다.
- 단위, manager 경계, Extension Host E2E 검증이 통과한다.

### 3.5. requirements-and-constraints

- Requirements and Constraints
- Workspace tablist는 Dashboard, Editor, Kanban, Context 순서의 네 탭을 제공해야 한다.
- 저장된 selectedTab이 design 또는 view이면 editor를 선택해야 한다.
- Editor는 프로젝트의 canonical Intake, Specification, Work Unit package를 탐색해야 한다.
- Editor는 선택한 artifact의 sectioned JSON 구조를 트리와 읽기 전용 미리보기로 표시해야 한다.
- 수정 가능한 semantic field는 구조화된 control로 편집하고 저장은 해당 artifact manager의 allowlisted 명령으로 수행해야 한다.
- 저장 성공 후 canonical package를 다시 읽고 manager validation 결과를 표시해야 한다.
- Webview 입력으로 임의 executable path, shell command 또는 raw filesystem write를 허용하지 않는다.
- Extension Host가 project root, package identity, artifact type, manager allowlist와 message allowlist를 소유한다.
- 공통 읽기 모델과 artifact별 쓰기 adapter를 분리한다.
- 기존 Kanban controller, manager 실행 및 capability 계약을 변경하지 않는다.
- canonical artifact JSON은 manager 외 경로로 수정하지 않는다.
- 네 탭의 순서, 접근 가능한 tablist, 키보드 탐색과 selectedTab 이전이 검증된다.
- Editor 트리는 Intake, Specification, Work Unit과 해당 section을 표시한다.
- 선택 artifact의 JSON 미리보기는 읽기 전용이며 textContent 기반으로 렌더링된다.
- 구조화 편집 요청은 allowlisted artifact manager와 semantic operation으로만 실행된다.
- 경로 이탈, symlink package, 미지원 artifact, 임의 manager 명령과 malformed message를 실행 전에 거부한다.
- 저장 성공과 manager validation 실패 모두 authoritative refresh 및 오류 경계로 검증된다.
- 기존 Kanban unit, manager integration과 Extension Host E2E가 통과한다.
