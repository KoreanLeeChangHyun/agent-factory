# 사용자 코드 기반 커스텀 작업 구조 조사

- 조사일: 2026-09-14 · 분류: 가공 자료(Processed) · 상태: 공식 자료 조사와 미승인 설계 제안

- 사용자의 최신 방향은 **사용자가 코드를 작성하고 플랫폼이 공통 에셋을 제공하는 방식**이다. AI의 코드 작성을 활용한다. 언어·라이브러리·SDK·격리 기술·파일 배치는 아래의 검토안이며 확정 결정이 아니다. 이번 작업은 조사 문서 작성만 수행했다. 제품 코드·기존 명세를 변경하거나 의존성을 설치하지 않았으며 테스트·빌드·배포도 실행하지 않았다.

- 관련 자료: [기록된 제품 개요](../../skills/design-platform/SKILL.md#product-overview) · [목표 디렉터리 구조](../../skills/rule-workbench-structure/SKILL.md#target-structure) · [외부 DB 조사](../research-external-db-custom-work/SKILL.md) · [플랜·조직·권한 조사](../research-saas-plans-organization-permissions/SKILL.md). 이전 문서의 작성 언어 미정·JSON 전용 설명은 이번 사용자 방향을 아직 반영하지 않은 부분이 있으므로 그대로 구현하지 않는다.

<a id="결론--코드-작성의-자유와-플랫폼-권한을-분리한다"></a>

## 1. 결론 — 코드 작성의 자유와 플랫폼 권한을 분리한다

- **우선 검토안:** TypeScript + React로 커스텀 작업을 작성하고, 플랫폼의 공통 UI 패키지와 SDK를 사용한다. 플랫폼은 고정된 빌드 절차로 정적 산출물을 만들고, 인증 화면과 분리된 출처의 격리 화면에서 실행한다. 공통 UI만 조립하도록 제한하지 않고 자체 컴포넌트도 허용하되, 호스트 화면·비밀·DB에 직접 접근하는 권한은 부여하지 않는다.

- 이는 아래 사례를 요구사항에 대입한 **우리 설계에 대한 판단**이다. TypeScript·React의 채택 자체가 보안을 보장하지 않고, AI가 잘 작성한 코드도 일반 사용자 코드와 같은 검증·격리·권한 절차를 거친다. 서버에서 임의의 사용자 코드를 실행하는 기능은 화면 코드 지원과 별도로 결정한다.

```text
사용자 / AI의 소스 코드 + 등록 정보 + 의존성 잠금
  → 격리된 빌드 → 검토 가능한 미리보기 → 불변 릴리스
  → 워크스페이스에 특정 릴리스 활성화
  → 서버가 허용한 작업 목록 → 선택한 작업의 격리 화면
  → SDK 메시지 → 호스트 중계 → 서버의 현재 권한 검사
  → 공유 비즈니스 로직 → 외부 DB / 에이전트 / 문서 등

공통 에셋: 컴포넌트 골격 + 데이터 인터페이스 + 테마
등록 정보: 이름·아이콘·진입점·요구 기능·호환 버전
사용자 코드: 실제 화면·상태·상호작용
```

## 3. 렌더링 구조 선택지

| 구조 | 강점 | 비용·제약 | 판단 |
| --- | --- | --- | --- |
| 호스트 React 트리에 사용자 모듈 직접 로드 | 공통 컴포넌트·상태·팝업 연결이 간단함 | 사용자 코드가 호스트의 실행 권한과 DOM을 공유함. 코드 분할 기능을 보안 경계로 볼 수 없음 | 신뢰하지 않는 고객 코드의 기본 방식에서는 제외 제안 |
| 별도 출처의 sandboxed iframe + SDK | 사용자 DOM·CSS·React 라이브러리를 활용하기 쉬움. 호스트와 메시지로 연결 | 포커스·단축키·팝업·높이·테마·영역 간 상태를 명시적으로 연결해야 함. iframe마다 자원 비용 발생 | **자유로운 사용자 컴포넌트를 위한 우선 후보** |
| 격리 코드 + Remote DOM + 호스트 컴포넌트 | 실제 렌더링을 호스트가 통제해 테마·공통 UI를 일관되게 제공하기 좋음 | 허용 요소·속성·이벤트 프로토콜을 설계해야 함. DOM 측정·Canvas·에디터 등은 호환성 검토 필요 | 공통 에셋 위주 확장을 더 중시하면 비교 검증할 후보 |
| 선언형 JSON 화면만 지원 | 검증·컴포넌트 통제를 좁게 설계할 수 있음 | 사용자 코드 중심이라는 최신 방향과 맞지 않음 | 등록 메타데이터에 활용하되 화면 작성의 유일한 형식으로 제한하지 않음 |

- 이 표의 적합성 평가는 설계 제안이다. iframe의 경계는 [MDN iframe 문서](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe), 원격 렌더링 메커니즘은 [Remote DOM 공식 설명](https://raw.githubusercontent.com/Shopify/remote-dom/main/README.md)을 근거로 비교했다. 두 실행 방식을 처음부터 모두 구현하기보다 필요한 커스텀 화면 사례로 하나를 선정하는 편을 제안한다.

## 4. 공통 에셋과 SDK는 다른 계약이다

| 제공 대상 | 제안 내용 | 포함하지 않을 것 |
| --- | --- | --- |
| 공통 UI | Button·Form·Table·Tree·Empty/Error/Loading 상태·패널 골격·선택적 탭 등의 실제 컴포넌트와 타입 | 조직이나 특정 작업에 종속된 샘플 데이터, 서버 자격증명 |
| 테마·에셋 | 의미 기반 색·간격·타이포그래피·아이콘, 현재 테마 전달과 변경 구독 | 호스트의 DOM 구조나 전역 CSS에 대한 직접 의존 |
| SDK | 등록 데이터 작업 호출, 탐색 요청, 작업 실행·상태 구독, 테마·지역화·뷰 상태 연결 | 임의 SQL 실행권, 임의 URL 프록시, 플랫폼 내부 HTTP 클라이언트 전체, 장기 토큰 |
| 작성 지원 | 버전별 타입 선언, API 문서, 예제·템플릿, 오류 코드·파일·행·열 진단, 지원 기능 목록 | AI가 문맥으로 추측해야만 사용할 수 있는 암묵적 규칙 |

- 패키지를 공통으로 제공한다는 것은 같은 버전의 공개 API를 쓴다는 뜻이지, 호스트와 동일한 React 인스턴스를 공유해야 한다는 뜻은 아니다. 격리 화면은 자체 번들에 검증된 UI 의존성을 포함할 수 있다. 초기에는 버전을 고정하고, 이후 공통 캐시 최적화를 검토하는 안이다.

- 테마 연동의 참고 사례로 [Forge 테마 API](https://developer.atlassian.com/platform/forge/design-tokens-and-theming/)는 호스트 테마를 적용하고 변경에도 반응한다. 우리도 “골격 + 데이터 + 테마”를 공통 계약으로 제공하되, 자유로운 사용자 CSS가 항상 디자인 일관성을 지킨다고 보장할 수는 없다. 강제할 범위와 권장할 범위를 구분해야 한다.

## 5. 작업 목록·사이드바·패널을 어떻게 결합할 것인가

- **제안:** 작업 목록과 외곽 레이아웃은 호스트가 소유한다. 서버가 현재 사용자에게 허용한 등록 정보를 반환하고 호스트가 이름·아이콘·선택 상태를 표시한다. 사용자 코드가 작업 목록 전체를 교체하거나 다른 작업 위에 UI를 덮도록 허용하지 않는다.

- 사이드바가 없으면 진입점을 선언하지 않으며 호스트가 공간을 예약하지 않는다.

- 커스텀 사이드바가 있으면 전용 격리 뷰에 로드한다. 패널과 같은 릴리스의 다른 진입점으로 둘 수 있다.

- 패널은 별도 격리 뷰에 로드한다. 패널 내부 탭은 사용자 코드가 공통 Tabs 컴포넌트로 구성하거나 생략하는 안이다. 호스트가 관리하는 전역 탭까지 필요한지는 별도 결정이다.

- 사이드바의 선택 → 패널 변경은 함수나 React 객체 공유가 아니라 크기가 제한된 직렬화 메시지·상태 계약으로 연결한다.

- 뷰 상태 범위는 사용자·워크스페이스·작업 활성화·릴리스·뷰 인스턴스로 구분한다. 로그아웃·전환 시 구독을 끊고 이전 응답을 폐기한다.

- 팝업·모달을 프레임 바깥에 표시하려면 호스트의 제한된 호출을 사용한다. 포커스 이동·키보드 접근성·IME·크기 변경·스크롤 정책을 정의한다.

- 각 영역에 iframe을 두는 방식은 상태 동기화와 메모리 비용이 있다. 작업마다 계속 유지하지 않고 선택 시 로드하고 숨김·종료 시 상태를 저장하는 후보를 비교한다. [VS Code 상태 복원 문서](https://code.visualstudio.com/api/extension-guides/webview#persistence)도 상태 저장과 화면 유지의 비용을 구분한다. 이를 우리의 수명 정책으로 그대로 확정하지는 않는다.

- 스탠다드 작업과 커스텀 작업은 같은 표시·탐색·데이터 계약을 따를 수 있지만, 신뢰 수준까지 같지는 않다. 스탠다드 화면의 신뢰된 React 렌더링과 커스텀 격리 호스트를 하나의 런타임 진입부가 구분해 배치하는 안이다.

<a id="작성컴파일게시활성화"></a>

## 6. 작성·컴파일·게시·활성화

| 도구 후보 | 확인 내용 | 적용 제안 |
| --- | --- | --- |
| [esbuild](https://esbuild.github.io/content-types/#typescript) | TS·TSX 변환을 지원하지만 타입 검사는 하지 않음 | 고정된 플랫폼 번들 파이프라인 후보. 별도 타입 검사와 계약 검증 필요 |
| [Vite](https://vite.dev/guide/build.html) | 정적 호스팅용 운영 빌드를 제공 | 로컬 작성 환경과 빌드 후보. 사용자 설정·플러그인 실행 여부를 통제해야 함 |
| [Sandpack](https://sandpack.codesandbox.io/) | 편집·미리보기·의존성·오류 표시 등 라이브 코딩 구성 요소 제공 | 작성 환경 후보일 뿐, 게시·권한·격리를 모두 해결하는 제품 런타임으로 간주하지 않음. 로컬 운영 적합성·외부 전송·자체 호스팅은 추가 확인 필요 |

- **제안 빌드 계약:** 소스 스냅샷·등록 정보·의존성 잠금을 입력으로 받아, 플랫폼이 관리하는 고정 도구로 타입·계약 확인 후 번들링한다. 고객의 임의 build 명령·플러그인·설정 코드를 기본 허용하지 않는다. 승인된 의존성의 고정 버전과 전이 의존성을 관리하고, 사설 패키지 자격증명은 별도 설계 전 제외한다.

- [npm 공식 문서](https://docs.npmjs.com/cli/v11/commands/npm-ci/)에 따르면 설치 스크립트를 끌 수 있지만, 명시적인 `npm run` 등은 해당 스크립트를 여전히 실행한다. 따라서 설치 옵션 하나로 빌드 격리가 완성되지 않는다. 컴파일러 자체의 취약점과 파일 읽기·자원 소모도 고려해 일회성 제한 실행 환경이 필요하다. 구체적인 격리 기술은 아직 선정하지 않았다.

```text
소스 스냅샷
  → 빌드 요청(멱등 키) → 큐 → 격리 실행 → 산출물 검증
  → 미리보기 / 진단 → 게시 권한 검사 → 불변 릴리스
  → 활성화 권한 검사 → 워크스페이스의 버전 포인터 변경

릴리스 기록 후보:
  소스·의존성 잠금·산출물 해시
  도구체인·SDK·UI·등록 스키마 버전
  진입점·요구 기능·빌드 결과·게시자·게시 시각
```

- 소스와 산출물은 접근 제어된 저장소에 보관하고, 운영 DB는 소유·버전·활성화·감사 메타데이터를 보관하는 안이다. 게시된 파일은 덮어쓰지 않는다. 빌드 실패·게시 실패 시 기존 활성 버전은 유지하고, 롤백은 검토된 이전 릴리스로 활성화 포인터를 변경한다. 권한 회수나 보안상 차단된 릴리스까지 롤백으로 복구하지 않는다.

- 미리보기도 사용자 코드를 실행한다. 운영과 같은 격리·권한 경계를 사용하고, 기본 샘플 데이터 또는 명시적으로 승인된 실제 데이터 접근을 구분한다. 미리보기 성공은 안전성 인증이 아니다. 여기서 기술한 검증은 향후 제품 빌드 절차이며 이번 조사에서 테스트를 실행했다는 뜻이 아니다.

<a id="반드시-분리해서-설계할-보안-경계"></a>

## 7. 반드시 분리해서 설계할 보안 경계

| 경계 | 제안 정책 | 남은 검토 |
| --- | --- | --- |
| 브라우저 화면 | 인증 앱과 다른 출처, 최소 sandbox 권한, CSP·브라우저 기능 제한. 호스트 토큰·공유 쿠키에 접근하지 않음 | 테넌트/릴리스별 출처·저장소 격리, 쿠키 도메인, 최상위 직접 열기, 정적 파일 접근 통제 |
| 메시지 중계 | 출처·송신 창·현재 뷰 세션·릴리스·메시지 스키마·크기·호출 빈도 확인. 임의 함수·URL 중계 금지 | 출처가 불투명한 sandbox의 연결 절차, 메시지 포트 수명·취소·재전송·시간 초과 |
| 서버 데이터/동작 | 현재 신원·회원 상태·권한·활성 버전·허용 동작 확인. DB 비밀은 서버만 보유 | 연결별 읽기/쓰기·승인·행/열 범위·작업 중 권한 회수 |
| 빌드 실행 | 운영 비밀·레포·DB에서 격리. 파일 범위·네트워크·CPU·메모리·프로세스·시간·산출물 크기 제한 | 로컬 서버에서 사용할 격리 기술과 회수 절차, 동시 빌드 수·비용 한도 |

- [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)은 호스트와 동일 출처의 iframe에 `allow-scripts`와 `allow-same-origin`을 함께 적용하는 위험을 경고한다. 별도 출처와 쿠키 범위 설계가 필요하며 `sandbox` 속성만 추가했다고 완료 처리하면 안 된다.

- [MDN 메시지 보안](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage#security_concerns)은 송신자와 메시지 형식을 검사하고 정확한 수신 출처를 지정하도록 설명한다. 불투명 출처는 단순 문자열 비교로 신원을 증명할 수 없으므로 별도 연결 설계가 필요하다. SDK는 사용 편의 계층이며, 고객이 SDK를 우회해 직접 메시지를 보내도 호스트와 서버가 동일하게 거부할 수 있어야 한다.

- [Forge 문서](https://developer.atlassian.com/platform/forge/app-context-security/)도 브라우저에서 받은 컨텍스트를 권한 판단에 쓰지 말라고 명시한다. 우리도 클라이언트가 전달한 조직·워크스페이스 ID를 권한 증거로 사용하지 않는다. 허용 범위는 사용자 권한, 활성화에 승인된 기능, 호출 대상 정책, MCP인 경우 토큰 범위를 함께 제한하는 안이다.

- [Node.js 공식 문서](https://nodejs.org/api/vm.html)는 `node:vm`이 보안 장치가 아니라고 명시한다. 이를 사용자 서버 코드나 빌드 코드의 격리 수단으로 채택하지 않는다. iframe도 악성 무한 루프에 대한 엄격한 CPU 할당이나 모든 데이터 유출 방지를 보장하지 않는다. 화면이 읽을 수 있는 데이터의 최소화, 외부 통신·탐색 통제, 뷰 종료·복구를 함께 설계해야 한다.

<a id="개인조직별-소유와-화면-노출"></a>

## 8. 개인·조직별 소유와 화면 노출

- **제안 데이터 모델:** 작성 원본의 소유, 게시 릴리스, 워크스페이스 활성화, 사용자별 표시 설정을 분리한다. 개인 또는 조직 소유를 지원할 수 있는 형태를 검토하되, 공유·이관·조직 간 배포 규칙은 아직 확정하지 않는다. 고객마다 플랫폼 소스 디렉터리를 생성할 필요는 없다.

- 개인 플랜은 혼자 사용하며 조직 기능·초대가 없다. 추가 워크스페이스 구독이 공유 권한을 만들지는 않는다.

- 팀은 조직을 뜻한다. 별도의 하위 팀 도메인을 추가하지 않는다.

- 조직에서는 작성·게시·활성화·실행 권한을 구분하고, 소유자가 구성한 권한 집합과 연결하는 안이다.

- 등록 정보에 요청한 권한을 적는 행위는 권한 취득이 아니다. 활성화 시 허용하고 매 호출 때 현재 권한을 검사한다.

- 작업 목록에서 숨기는 개인 설정은 사용 권한과 별개다. 소스 열람, 릴리스 사용, 데이터 접근도 각각 구분한다.

- 엔터프라이즈에 승인 절차·외부 통신 정책 등을 추가할 수 있으나 기본 격리·비밀 보호·권한 검사는 모든 플랜에 필요하다.

- 워크스페이스 MCP는 같은 서버 동작 계약을 호출한다. 화면의 React 코드를 MCP 서버가 실행하거나, 조직의 모든 커스텀 기능을 자동 도구화한다는 뜻은 아니다. MCP에 노출할 동작과 그 입력·출력·권한·승인 요구를 별도로 정의한다.

<a id="목표-구조에-필요한-파일-책임--검토안"></a>

## 9. 목표 구조에 필요한 파일 책임 — 검토안

- 아래는 전체 트리를 확정하는 문서가 아니라 이번 조사로 식별한 책임의 배치안이다. **새 루트나 새 최상위 패키지를 추가하지 않는다.** 공개 SDK는 기존 `workbench-runtime` 내부의 독립 배포 진입점으로 시작하는 안이며, 독립 패키지가 필요해지면 이유와 영향부터 검토한다. TypeScript 빌드 실행부는 브라우저 의존성에 섞이지 않도록 어댑터의 별도 진입점으로 둔다.

```text
apps/
├── api/routes/workbenches.py              # 소스·빌드·게시·활성화 HTTP 진입
├── mcp/tools/workbenches.py               # 명시적으로 노출한 동일 유스케이스의 MCP 진입
├── web/components/WorkbenchHost.tsx       # 작업 목록과 선택적 사이드바·패널 결합
└── worker/jobs/workbench_build.py         # 빌드 작업 수신·권한/상태 확인·격리 실행 요청
packages/
├── core/workbenches/
│   ├── domain.py                         # 소스 스냅샷·빌드·릴리스·활성화 상태
│   ├── ports.py                          # 저장소·빌드 실행·산출물 저장 인터페이스
│   ├── policies.py                       # 게시·활성화·기능 승인·호환성 규칙
│   └── use_cases.py                      # 요청·완료·게시·활성화·롤백 흐름
├── adapters/
│   ├── workbench_build.py                # 격리된 빌드 실행기 호출·제한·취소 어댑터
│   ├── workbench_bundle.ts               # 고정 도구체인의 TS 번들 진입점; 별도 빌드 환경
│   └── object_storage/workbenches.py     # 권한 있는 소스·불변 산출물 저장/읽기
├── design-system/
│   ├── components/                       # 골격·데이터 props·상태·접근성
│   ├── theme.tsx                         # 테마 제공·적용
│   ├── tokens.css                        # 버전 관리되는 시각 토큰
│   └── assets/                           # 공통 아이콘·정적 에셋
├── workbench-runtime/
│   ├── renderer.tsx                      # 표준 화면 또는 커스텀 격리 화면 선택
│   ├── SandboxHost.tsx                   # 격리 뷰 생성·종료·복구
│   ├── bridge.ts                         # 호스트 메시지 검증·허용 SDK 호출 중계
│   ├── sdk.ts                            # 사용자 코드용 공개 진입점; 호스트 내부 코드 제외
│   ├── bindings.ts                       # 데이터 계약 호출·응답·취소
│   ├── actions.ts                        # 허용 동작·탐색·실행 요청
│   ├── view-state.ts                     # 사이드바/패널 선택 상태·수명 관리
│   └── registry.ts                       # 표준 작업·허용 에셋·호환 버전 조회
└── workbench-editor/
    ├── WorkbenchEditor.tsx               # 코드 작성·변경·게시 UI 조합
    ├── preview.tsx                       # 같은 격리 경계의 초안 미리보기
    └── diagnostics.ts                    # 파일·행·열·단계별 오류 표시
contracts/schemas/workbench/
├── manifest.schema.json                  # 이름·진입점·요구 기능·SDK 호환성
├── bridge.schema.json                    # 중계 요청·응답·이벤트·취소 형식
└── release.schema.json                   # 빌드 식별자·해시·불변 릴리스 정보
deploy/local/config/                      # 선정 후 로컬 빌드 격리·정적 출처·실행 서비스 설정
tests/packages/                           # 각 소유 패키지의 향후 검증
tests/integration/                        # 빌드→게시→활성화→권한·화면 흐름의 향후 검증
```

- 필요한 스키마 버전 경로, 매니페스트·lockfile·패키지 exports·빌드 설정·마이그레이션·테스트의 정확한 파일은 후속 계약에서 확정한다. 위 후보가 기존 파일의 내용·이력·의존성을 분석한 이동표를 대체하지 않는다. 실제 고객 소스·산출물은 런타임 저장소의 데이터이지 이 저장소의 고객별 소스 폴더가 아니다. `feedback/`·`uploads/`는 사용자의 디렉터리이며 빌드 저장소로 사용하지 않는다.

<a id="기존-명세에서-수정해야-할-충돌"></a>

## 10. 기존 명세에서 수정해야 할 충돌

- `.codex/skills/design-platform/references/workbench-runtime.md`에는 커스텀 작업은 실행 코드가 아닌 JSON 데이터이며 화면은 닫힌 레지스트리로만 구성한다는 설명이 있다. 최신 사용자 방향에 맞춰 다음을 수정할 필요가 있다. 이번 조사에서는 해당 명세를 수정하지 않았다.

- JSON 전용 화면 → 등록 정보 + 사용자 소스 + 빌드 산출물 계약.

- 동일 레지스트리 렌더러만 사용 → 공통 인터페이스 아래 신뢰된 표준 화면과 격리된 커스텀 화면 구분.

- 에디터의 에셋 조립만 허용 → 코드 작성·타입 지원·진단·미리보기·게시 흐름.

- 릴리스의 JSON 스냅샷만 저장 → 코드·의존성·도구체인·산출물·SDK 버전의 추적 가능한 불변 기록.

- 기존 권한 문서의 팀 멤버십 경로 → 사용자가 명시한 조직·권한 집합 모델과 정합성 검토.

- 불변 릴리스, 서버 권한 검사, 비밀 비노출, 취소와 오래된 응답 무시 같은 기존 원칙은 유지할 수 있다. 기존 선언형 데이터가 실제 저장되어 있는지는 별도 확인하고, 코드 기반으로 바꾼다는 이유로 이전 데이터를 삭제하거나 릴리스를 덮어쓰지 않는다.

<a id="후속-결정과-검증-계획"></a>

## 11. 후속 결정과 검증 계획

| 결정 | 우선 제안 | 확인할 사항 |
| --- | --- | --- |
| 작성 언어 | TypeScript + React | JS 허용 범위, 지원 버전, 사용자 에셋·스타일 형식 |
| 렌더링 | 별도 출처 iframe + 공통 UI·SDK | 일반 라이브러리 자유도가 필수인지, Remote DOM의 UI 통제가 더 중요한지 |
| 데이터/백엔드 | 등록 서버 동작을 SDK로 호출 | 사용자 서버 함수·SQL 작성·스키마 생성은 별도 요구로 결정 |
| 의존성/빌드 | 승인 의존성·고정 도구체인·일회성 격리 실행 | 로컬 서버 격리 기술·자원 예산·캐시·오류/취소 처리 |
| 배포 | 로컬 운영, 변경 불가 산출물과 활성 버전 고정 | 분리 출처의 DNS/TLS·쿠키·파일 접근 통제. AWS는 이후 어댑터/배포 타깃 전환 |

- 계약 이후 검증 대상으로는 공통 Table/Tree 기반 화면, 서드파티 차트, 사이드바 없는 작업, 사이드바 선택과 패널 연동, 탭 유무, 테마 전환·키보드·IME, 잘못된 SDK 요청, 권한 회수, 다른 조직 데이터 접근, 빌드 폭주·무한 루프·취소, 실패한 게시와 롤백을 제안한다. 사용자가 정한 전체 개편 후 테스트 단계까지 이번 조사에서 실행하지 않았다.

- 우선 위 결정으로 파일별 입력·출력·오류·권한·의존성·완료 조건을 채우고 전체 구조 계약을 갱신하는 것이 다음 단계다. 새 루트나 빈 디렉터리를 먼저 만드는 것은 필요하지 않다.

## 12. 조사 한계와 출처 사용 범위

- 공식 문서·공식 저장소만 기술 근거로 사용했다. 제품 내부 구현 감사, 성능 측정, 브라우저 검증, 라이선스·보안 유지보수 실사까지 수행한 것은 아니다. 라이브러리 이름은 도입 후보이며 정확한 버전·번들 크기·비용을 확정하지 않았다. Sandpack의 상세 bundler 페이지와 Remote DOM 문서 사이트는 조회에 실패했으며, 각각 공식 소개 페이지와 공식 저장소 원문에서 확인한 범위로만 서술했다. 정적 HTML 문서는 외부 스크립트·CDN 의존성 없이 작성했다.
