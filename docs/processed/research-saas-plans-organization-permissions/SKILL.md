# 유명 SaaS의 플랜·조직·사용자·권한 구조 조사

- 조사일: 2026-09-14 · 가공 자료(Processed) · 공식 문서 기반 · 설계 제안 미승인

- 요금 금액 비교보다 상품 구분, 소유 경계, 사용자 수명 관리, 권한 구성 방식에 집중했다. 제품별 용어를 우리 조직·워크스페이스와 동일시하지 않는다. 지역·결제 주기·배포 방식·계약에 따라 가격과 제공 범위가 달라지므로 구매 견적 자료가 아니다. 코드·설정·플랜·권한을 변경하지 않았고 테스트도 실행하지 않았다.

- 연결 자료: [제품 전체 그림](../../skills/design-platform/SKILL.md#product-overview) · [외부 DB·커스텀 작업 데이터 조사](../research-external-db-custom-work/SKILL.md) · [구조 계약](../../skills/rule-workbench-structure/SKILL.md#directory-contract).

<a id="우리-시스템에서-이미-정한-것"></a>

## 1. 우리 시스템에서 이미 정한 것

- 개인·팀·엔터프라이즈의 세 플랜. 개인은 1인 사용, 워크스페이스 1개 무료, 추가 개수에 따른 구독이며 조직 작업과 초대 기능이 없다.

- 팀 플랜부터 조직을 제공한다. 여기서 팀은 조직을 의미하고 별도 조직 하위 팀 계층이 아니다.

- 조직 소유자가 사용자를 초대하고 접근 범위와 조직 관리자 권한을 부여한다.

- 조직 소유자가 개별 권한을 묶어 권한 집합을 만들고 사용자에게 부여한다.

- 엔터프라이즈의 핵심 차별점은 보안이다. 구체적인 기능·가격·제한은 조사 후 결정한다.

- SaaS 관리자는 고객 조직 관리자와 별개다. 작업 화면·MCP·외부 DB 접근을 모두 관제해야 한다.

- 개인 플랜의 추가 워크스페이스 가격, 팀·엔터프라이즈 과금 단위, 동시 복수 조직 소속, 개인과 조직 구독의 동시 보유, 권한 합산·거부 규칙은 아직 확정되지 않았다.

<a id="공통점과-차이점"></a>

## 3. 공통점과 차이점

- **조사 해석:** 이 제품들은 대체로 상품 사용 가능 범위, 사용자 신원, 조직 소속, 대상별 접근 권한을 분리한다. 하지만 모든 제품이 개인→팀→기업의 동일한 계층을 쓰는 것은 아니다. GitHub는 무료 조직이 있고, Notion·Slack의 워크스페이스 의미도 우리 작업공간과 다르다. 우리 조직 모델을 경쟁사의 이름에 맞춰 바꿀 필요는 없다.

- **중요한 예외:** SSO를 엔터프라이즈만의 보편적 기준으로 볼 수 없다. Notion Business와 Slack Business+에도 SAML SSO가 있다. 따라서 엔터프라이즈를 ‘보안이 있는 플랜’이라고 정의하지 말고 보안 정책을 조직적으로 강제·자동화·감사하는 수준으로 비교해야 한다. [Notion 플랜](https://www.notion.com/pricing) · [Slack 플랜](https://slack.com/pricing).

- **우리 적용 제안:** 조직 소유자가 사용자 정의 권한 집합을 구성하는 기능은 팀 플랜의 기본 협업 기능으로 유지한다. 이를 엔터프라이즈 전용으로 올리는 것은 이미 설명한 제품 방향과 충돌한다.

<a id="분리해야-할-데이터-개념"></a>

## 4. 분리해야 할 데이터 개념

| 개념 | 질문 | 제안 책임 |
| --- | --- | --- |
| 사용자 계정 | 누구인가? | 로그인 신원·프로필·계정 상태. 조직별 권한을 계정의 단일 role 필드에 저장하지 않음 |
| 조직 소속 | 어느 조직에 소속되어 있는가? | 초대·가입·정지·탈퇴·제거 상태와 소유자 여부 |
| 구독·기능 제공 범위 | 구매한 상품으로 무엇을 쓸 수 있는가? | 개인/조직의 플랜·수량 한도·결제 상태. 누가 데이터에 접근할 수 있는지는 별도 |
| 개별 권한 | 무슨 행위를 할 수 있는가? | 초대·조회·편집·실행·게시·권한 부여 등 시스템이 실제로 검사하는 행위 |
| 권한 집합 | 어떤 권한을 묶는가? | 조직 소유자가 구성하는 이름 있는 권한 묶음 |
| 권한 할당 | 누가 어디에서 그 묶음을 사용하는가? | 사용자 + 권한 집합 + 적용 범위. 범위 종류와 상속은 후속 확정 |
| 보안 정책 | 어떤 조건에서 접근할 수 있는가? | SSO·세션·네트워크·장치·데이터 반출 등 채택된 조직 정책 |
| 감사 기록 | 누가 무엇을 바꿨는가? | 초대·역할·권한·보안 정책·작업 실행의 변경 근거와 결과 |

- 위 모델은 설계 제안이다. 사용자당 플랜 필드 하나로 조직 기능을 결정하면 개인 사용자와 조직 소속을 함께 다루기 어렵다. 개인 구독은 개인 소유 자원, 조직 구독은 조직 소유 자원에 적용하는 안을 권한다. 실제 동시 보유·복수 조직 지원은 사용자 결정이 필요하다. 엔터프라이즈도 우선 같은 조직 모델 위의 플랜과 보안 정책으로 검토하며 별도 기업 상위 계층을 자동 생성하지 않는다.

## 5. 우리 플랜의 기능 구분 후보

| 영역 | 개인 | 팀 | 엔터프라이즈 |
| --- | --- | --- | --- |
| 이용 주체 | 본인만 사용 — 확정 | 조직 소유자와 초대한 사용자 — 확정 | 조직 기반·보안 차등 — 방향 확정, 세부 미정 |
| 워크스페이스 | 1개 무료, 추가 개수별 구독 — 확정 | 개수·가격·인원 과금 미정 | 개수·가격·계약 방식 미정 |
| 조직·초대 | 없음 — 확정 | 제공 — 확정 | 팀 기능을 기반으로 검토 |
| 사용자 정의 권한 집합 | 본인 접근은 검사하되 타 사용자 할당 UI 불필요 — 제안 | 조직 소유자가 구성·할당 — 확정 | 동일 권한 엔진 + 고급 통제 — 제안 |
| 기본 보안 | 인증·서버 권한 확인·테넌트 격리·암호화·비밀 보호·접근 회수는 모든 플랜의 기준으로 제안. 고객용 감사 기능의 범위·기간과는 구분 |  |  |
| 조직 보안 자동화 | 별도 요구 없음 | SSO 포함 여부 등 미정 | SSO 강제·SCIM·도메인 검증·감사 연동·세션 정책 등을 후보로 조사 |

- 유료 플랜은 사용자에게 권한을 자동 부여하지 않는다. 반대로 조직 소유자도 플랜이 제공하지 않는 기능을 권한 집합에 넣는 것만으로 활성화할 수 없다.

<a id="관리자-역할을-어떻게-나눌-것인가"></a>

## 6. 관리자 역할을 어떻게 나눌 것인가

- Atlassian의 역할 분리, Notion의 membership admin, Slack의 system role을 참고한 우리 설계 후보다. 명칭과 기본 제공 개수는 미확정이다.

```text
조직 소유자                # 소유권·관리자 지정·권한 집합의 최종 관리
조직 관리자                # 위임받은 조직 관리 기능
사용자 관리자              # 초대·가입·정지·제거 (후보 권한 집합)
권한 관리자                # 허용 범위의 권한 집합·할당 관리 (후보)
청구 관리자                # 구독·청구 관리 (후보)
보안 관리자                # 채택된 보안 정책·감사 관리 (후보)
일반 사용자                # 부여된 범위의 스탠다드·커스텀 작업
SaaS 관리자                # 플랫폼 운영자. 위 조직 역할과 별도
```

- 이 이름마다 별도 사용자 종류나 클래스가 필요한 것은 아니다. 소유권과 플랫폼 운영자 경계를 제외한 위임 업무는 권한 집합으로 표현할 수 있다. 관리자가 자동으로 모든 문서·DB 데이터에 접근하는지 여부도 별도 정책이다. 기존 저장소 정책은 조직 소유자도 내용 읽기에는 워크스페이스 멤버십을 요구하므로, 이를 변경하려면 명시적 결정이 필요하다.

- 최소 한 명의 유효한 소유자 유지, 소유권 이전·조직 삭제·청구 변경의 추가 확인, 자기 권한 상승 방지를 제안한다. 권한 할당 변경뿐 아니라 이미 여러 사용자에게 할당된 권한 집합의 내용 수정도 권한 상승 경로이므로 검토·감사해야 한다. 조직 관리자에게 어디까지 위임할지는 아직 미정이다.

<a id="사용자-수명-관리-제안"></a>

## 7. 사용자 수명 관리 제안

```text
초대 생성 → 수신자 확인·수락 → 활성 멤버십 → 범위별 권한 부여
                             → 정지 → 접근 회수 → 복구 또는 제거
초대 미수락 → 만료 또는 취소
```

- 초대와 실제 계정·멤버십을 분리한다. 초대받은 이메일의 통제 여부를 확인하고 수락 시점의 초대·조직 상태를 다시 검사한다.

- 조직에서 제거하는 것은 전역 계정을 삭제하는 것과 다르다. 개인 자원이나 다른 조직 소속을 함께 삭제하지 않는다.

- 정지·제거 시 웹 세션뿐 아니라 MCP 토큰, 실행 중·대기 작업, 데이터 작업, 캐시 접근도 해당 조직 범위에서 회수해야 한다. 장기 실행은 안전한 경계에서 재인가하고 이미 완료한 부수 효과는 별도로 기록한다.

- 재가입 시 과거 권한을 자동 복원할지 결정한다. 경쟁사의 복원 동작을 그대로 채택하지 않는다.

- 공유 자원은 퇴사자의 개인 소유 토큰에 영구 의존하지 않도록 소유·자격증명 이전 정책을 정한다. 비인간 실행 주체는 별도 후속 설계다.

- SCIM 도입 시 IdP가 관리하는 필드·소속과 앱 내부의 관리 권한을 구분하고, 동기화 지연·실패·수동 변경 충돌·긴급 복구 경로를 정한다.

- 공식 사례: GitHub EMU는 IdP 기반 계정·소속 관리, Notion은 Enterprise SCIM과 전용 관리 권한을 설명한다. SSO는 로그인 방식이고 SCIM은 사용자 수명 관리이므로 둘을 같은 기능으로 묶어 구현하지 않는다. [GitHub EMU](https://docs.github.com/en/enterprise-cloud@latest/admin/concepts/identity-and-access-management/enterprise-managed-users) · [Notion SCIM](https://www.notion.com/help/provision-users-and-groups-with-scim).

<a id="권한-계산과-ui"></a>

## 8. 권한 계산과 UI

```text
허용 = 활성 신원
    AND 활성 개인 소유권 또는 조직 멤버십
    AND 대상 워크스페이스·작업의 유효한 권한
    AND 플랜 제공 범위
    AND 채택한 조직 보안 정책
    AND (MCP면 토큰의 범위)
```

- 제안 초기 규칙은 범위가 일치하는 허용 권한의 합산 + 계정 정지·조직 탈퇴·범위 불일치 같은 강제 차단이다. 사용자 정의 명시적 거부와 다중 상속은 복잡성이 커 별도 요구가 있을 때 도입하는 안이다. Retool의 합산 모델은 참고 사례일 뿐 우리 정책의 승인 근거가 아니다.

- 관리 화면에는 사용자별 유효 권한과 출처를 보여주는 것이 좋다. 예: ‘워크스페이스 A의 실행 권한 — 운영자 권한 집합에서 부여’. 거절 시 플랜 제한·권한 부족·조직 정지·보안 정책 위반을 관리자에게 구분해 보여주되 비인가 사용자에게 자원 존재나 민감한 설정을 노출하지 않는다. 변경 전 영향받는 사용자와 작업을 미리 보여주도록 제안한다.

- 스탠다드·커스텀 작업 목록은 유효 권한에 맞춰 구성한다. 화면에서 숨기거나 버튼을 비활성화하는 것은 사용자 경험일 뿐, API·MCP·worker의 서버 권한 검사 대체가 아니다. 외부 DB 행·열 권한은 [데이터 조사](../research-external-db-custom-work/SKILL.md)에서 설명한 별도 경계를 유지한다.

<a id="과금과-플랜-변경에서-결정할-것"></a>

## 10. 과금과 플랜 변경에서 결정할 것

- 개인은 합의한 워크스페이스 개수 과금을 유지한다. 팀은 멤버 수·워크스페이스 수·기본 구독+사용량 중 선택해야 한다. 사용자 단위 과금은 초대·정지·활성·외부 사용자 중 무엇을 과금 인원으로 세는지 정해야 한다. Retool처럼 작성자와 이용자를 나누는 방식은 참고할 수 있지만 편집 행위에 따른 과금 변경 안내와 예측 가능성이 필요하다.

- 제안: 기능 제공 정책과 결제 구현을 분리한다. 구독 변경·결제 웹훅은 중복·지연·역순을 처리하고, 결제 실패가 사용자 데이터 삭제나 보안 통제 해제로 이어지지 않게 한다. 권한 부여는 과금 좌석 생성과 동일한 행위가 아니다.

- 개인→팀: 개인 작업공간을 자동 조직 소유로 바꿀지, 명시적으로 이전할지 결정. 연결 자격증명과 작업 소유권도 포함한다.

- 팀→개인: 조직 멤버와 공유 자원을 단순히 숨기지 않는다. 이전·내보내기·접근 종료 정책이 먼저 필요하다.

- 엔터프라이즈→팀: SSO 강제·SCIM·네트워크 정책을 갑자기 끄지 않는다. 대체 로그인·관리자 접근·회수 상태를 확인한다.

- 수량 초과: 신규 생성 제한·유예·읽기 전용 등의 정책을 선택하되 즉시 삭제는 기본 동작으로 제안하지 않는다.

<a id="디렉터리와-파일-책임에-미치는-영향"></a>

## 11. 디렉터리와 파일 책임에 미치는 영향

- 아래는 전체 파일 명세가 아닌 책임 후보이며 새 구조를 생성하지 않는다.

```text
packages/core/
├── identity/                    # 계정·신원·세션·인가의 공통 규칙
├── organizations/               # 조직·초대·멤버십·권한 집합·할당
├── workspaces/                  # 개인/조직 소유와 작업공간 접근 범위
├── billing/                     # 후보: 구독·수량·기능 제공 정책
├── audit/                       # 권한·멤버십·정책 변경 이력
└── administration/              # SaaS 운영자 기능. 조직 관리자와 분리

packages/adapters/
├── identity/                    # 인증 제공자·향후 기업 IdP 연동
└── postgres/                    # 계정·소속·권한·구독 저장 구현

apps/api/routes/                 # 조직·사용자·권한·구독의 HTTP 계약
apps/mcp/                       # 동일 공통 인가 + 토큰 범위 검사
apps/worker/                    # 실행 시 재인가·향후 동기화/회수 작업
apps/web/pages/
├── organization/                # 조직·멤버·권한 집합·보안 설정 화면 후보
├── account/                     # 본인 계정·개인 구독 화면 후보
└── admin/                       # SaaS 관리자 화면 후보
```

- 권한 판정을 API/MCP/web에 각각 구현하지 않는다. 조직 사용자 관리 화면이 전역 계정 삭제 기능을 직접 소유하지 않도록 한다. 내부 정책의 별도 팀 계층과 과거 경로는 이번 사용자 요구와 충돌하므로 후속 명세에서 정리할 대상이며, 이번 조사로 자동 변경하지 않았다.

<a id="다음-확정-순서"></a>

## 12. 다음 확정 순서

- 개인 계정·조직 소속·구독 주체의 관계와 복수 조직 허용 여부.

- 조직 소유자 전용 행위와 조직 관리자에게 위임할 수 있는 행위.

- 권한 목록·권한 집합·할당 범위·상속·합산·차단 규칙.

- 초대·정지·제거·재가입·소유권 이전 및 MCP/작업 실행 접근 회수.

- 팀 과금 기준과 플랜별 기능 제공 범위.

- 엔터프라이즈의 첫 보안 제공 범위와 단계별 확장 후보.

- 디렉터리 책임·파일별 구현 명세·입출력·이전 대응표·검수 시나리오.

- 권고 요약: 개인·팀·엔터프라이즈라는 상품 구분은 유지하되, 하나의 계정·권한 엔진에 소유 범위와 상품 제공 정책을 결합한다. 팀부터 사용자 정의 권한 집합을 제공하고, 엔터프라이즈는 같은 조직 모델 위에서 보안 정책과 사용자 관리 자동화를 강화하는 안이 현재 요구와 가장 일관적이다. 이는 비교 자료로부터 도출한 제안이며 아직 확정 명세가 아니다.
