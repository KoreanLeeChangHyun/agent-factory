# 도메인·서비스·데이터·배포 경계 설계 초안

- 문서 ID: `service-boundary-001` · 초안 2 · 2026-09-15.

- **설계 검수 전**: 독립 배포·DB 분리 수준·장애 정책은 인터뷰에서 결정했다. 서비스 수·묶음·구현 기술은 미확정이다.

- 사용자 요청: SaaS의 경계를 먼저 설계하고 디렉터리·파일 명세에 연결한다.

- 추가 근거: [7개 질문의 인터뷰 기록](../interview-service-boundaries/SKILL.md). 원문 선택·추천·미결정 항목은 기록에서 보존한다.

- 후속 상세안: [실행 흐름과 API·데이터 계약 초안](../analyze-execution-contracts/SKILL.md). 접수·시작 분리, 사용권, 취소, 감사 전달을 구체화했다. 검수 전 제안이다.

- 이번 개정은 가공 설계안에 결정을 반영한 것이다. 기존 영문·한국어 명세의 전체 정합화는 아직 완료하지 않았다.

- 기준: [제품 요구사항](../../skills/design-platform/SKILL.md#product-overview) · [현재 목표 구조](../../skills/rule-workbench-structure/SKILL.md#target-structure) · [구조 계약](../../skills/rule-workbench-structure/SKILL.md#directory-contract).

- 현재 구조를 대체하지 않는다. 코드 이전·서비스 기동·DB 변경은 수행하지 않았다.

<a id="확정-조건과-설계-기준"></a>

## 1. 확정 조건과 설계 기준

- **확정**: 클라우드 관제, 개인·조직 워크스페이스, 표준·사용자 코드 기반 작업.

- **확정**: 외부 DB 연결, 워크스페이스 MCP, 사람 채팅과 에이전트의 권한 있는 읽기.

- **확정**: 과금과 독립된 사용량 한도, 현재 로컬 배포, 향후 AWS.

- **제안**: 8개 업무 서비스 후보. 화면 개수나 테이블 개수와 일대일로 맞추지 않는다.

- 함께 저장해야 하는 데이터는 같은 서비스에 두는 것을 우선한다.

- 다른 서비스의 DB에 직접 접근하지 않고 공개 API·이벤트로 연결한다.

- 서비스·DB 이름은 설계 식별자다. 그대로 새 디렉터리를 만들라는 지시가 아니다.

<a id="분리-수준"></a>

### 1.2. 분리 수준

- 도메인: 규칙·데이터·용어의 소유권.

- 서비스: 외부 계약·실행·배포의 독립 단위.

- DB: 서비스가 독점 접근하는 저장소.

- 물리 호스트: 자원과 장애를 공유하는 인프라 단위.

- **별도 프로세스·DB를 같은 서버에서 실행해도 서버 장애는 함께 겪는다.**

## 2. 도메인·서비스·데이터 대응표

- 모든 행은 초안이다. 소유 데이터의 정확한 테이블·필드는 후속 파일 명세에서 확정한다.

- 각 DB의 접근 계정·마이그레이션 계정은 별도로 둔다.

| 서비스 후보 | 업무 도메인 | 권위 있는 데이터 | 묶거나 분리한 이유 |
| --- | --- | --- | --- |
| S1 접근 관리<br>`access_db` | identity · organizations | 계정·세션·토큰·조직·멤버십·권한 집합·범위별 할당 | 회원 정지·권한 회수의 일관성. 워크스페이스 ID는 참조만 소유. |
| S2 작업공간·작업<br>`workspace_db` | workspaces · workbenches · appearance | 소유 유형·소유자 ID·작업 정의·빌드 요청·릴리스·사용 설정·테마 설정 | 워크스페이스 상태와 작업 활성화를 함께 검사·저장. 세션·권한 원본은 S1. |
| S3 실행·일정<br>`execution_db` | agents · planning · scheduling · reporting | 에이전트 버전·계획·일정·Run·실행 Job·실행 이벤트·결과 보고 | Run과 실행 Job의 원자적 생성 유지. 보고 접수는 에이전트 자동 기동이 아님. |
| S4 문서<br>`documents_db` | knowledge | 문서·불변 리비전·출처·객체 참조·검색 인덱스 | 파일·검색·보존 수명과 실행 업무를 분리. 검색 결과는 파생 데이터. |
| S5 채팅<br>`chat_db` | chat | 대화·메시지·변경 커서·전달 대기 기록 | 실시간 연결 부하를 격리. DM·채널 범위·참여 모델은 미정. |
| S6 연결·외부 데이터<br>`connections_db` | connections · 후보 data_access | 연결 메타데이터·암호화 자격증명·OAuth 상태·웹훅·수집 체크포인트 | 같은 연결을 연동·DB 화면이 공동 사용. 고객 DB 내용의 소유권을 가져오지 않음. |
| S7 사용량<br>`usage_db` | usage | 한도 설정·사용량 이력·계측 이벤트 식별자 | 가격·청구와 독립. 현재 사용권·카운터는 이 서비스가 소유한 Redis 영역에서 집행. |
| S8 감사<br>`audit_db` | audit | 추가 전용 보안 감사 기록·수신 중복 방지 기록 | 다른 서비스의 감사 이력 수정 방지. 진단 로그·실행 결과 보고와 구분. |

<a id="독립-업무-서버로-만들지-않는-영역"></a>

### 2.1. 독립 업무 서버로 만들지 않는 영역

- `contracts`: 데이터 계약 도메인. schemas 원본과 py·ts 생성 코드 소유. 상주 서버·DB는 필요하지 않다.

- `design-system`: 공통 컴포넌트·테마·에셋 패키지.

- `workbench/sdk·runtime·editor`: 브라우저·호스트 도구. 별도 업무 DB를 만들지 않는다.

- `workbench/build`: 격리 환경의 빌드 도구. 빌드 상태의 원본은 S2.

- `administration`: 각 서비스의 관리자 계약을 조합한다. 전 서비스 DB를 직접 수정하는 우회 계정은 금지한다.

- `shared`: 최소 공통 타입·순수 함수. 다른 서비스의 업무 로직을 호출하는 뒷문이 아니다.

- `billing`: 후속 설계. 구독·결제 원본을 S7에 섞지 않는다.

- 제품의 테스트 작업: 별도 실행 도메인은 미확정. 개발 검증용 `tests/`와 구분한다.

### 2.3. 서비스 묶음 검토 결과 — 제안

| 묶음 | 유지하는 이유 | 분리 재검토 조건 |
| --- | --- | --- |
| S1 identity·organizations | 계정 정지·멤버십·권한 변경의 소유권을 한곳에 유지. | 외부 IAM 위임·독립 조직 관리 요구가 생길 때. |
| S2 workspace·workbench | 활성 작업·릴리스·작업공간 상태의 로컬 변경 경계 유지. | 조직 간 마켓 배포가 확정되면 정의 카탈로그와 사용 설정 분리 검토. |
| S3 실행·일정·보고 | Run·실행 Job의 원자성 유지. 실행 보고 원본을 감사 서비스와 혼합하지 않음. | 분석용 보고 부하 증가 시 읽기 모델만 분리. |
| S4 문서 / S5 채팅 | 파일·리비전·검색 수명과 메시지·연결 부하를 분리. | 현재는 기능·부하 측정 전. 공통 내용이라는 이유만으로 합치지 않는 제안. |
| S6 연결·외부 데이터 | 자격증명 소유권과 원천 접근을 같은 경계에 둠. | 데이터셋 물리 수집·연합 조회의 실행 부하를 정의한 뒤 데이터 처리 서비스 분리 여부 판단. |
| S7 사용량 / S8 감사 | 동기 자원 허용과 비동기 추가 전용 증빙의 장애 특성 구분. | DB 인스턴스를 공유하므로 논리 분리가 물리 장애 격리인 것은 아님. |

- 8개는 계속 검수 후보로 유지한다. 테이블·호출 계약 검토 전 최종 개수를 확정하지 않는다.

## 3. 호출·공개 계약

<a id="calls-diagram"></a>

<a id="요청-경로-다이어그램"></a>

### 3.1. 요청 경로 다이어그램

- **1. 외부 진입**웹 → API<br>에이전트 → MCP

- **2. 소유 서비스**신원·범위 확인<br>업무 판단·저장

- **3. 후속 실행**서비스 Outbox → 전달<br>소유 서비스 작업자 → 결과

- 독립 서비스 방향을 적용한 제안 경로. 읽기 요청은 후속 실행 없이 결과를 반환한다.

- API·MCP는 서비스 클라이언트로 요청한다. 소유 서비스의 업무 코어·DB를 직접 실행하지 않는다.

- 서비스 내부에서는 자기 core·adapters를 사용한다. 모든 서비스가 전체 core를 함께 배포할 필요는 없다.

- 공유 계약의 배포 버전은 고정한다. 원본 스키마 변경으로 모든 서비스를 동시에 배포하도록 만들지 않는다.

- 동기 호출에는 제한 시간·취소 전파·명시적 실패를 둔다. 내부 프로토콜은 아직 미선정이다.

- 이벤트에는 event_id·생산자·계약 버전·테넌트·집합체 ID·revision·상관관계 ID를 제안한다.

- 이벤트의 사용자·테넌트 값만으로 권한을 인정하지 않는다.

| 호출 | 목적·방식 | 장애 시 기준 제안 |
| --- | --- | --- |
| API/MCP → 소유 서비스; S1은 신원·권한 검사 | 신원 확인 후 서비스별 자원 권한 검사 | 검증 불가 시 허용하지 않음. 프록시가 전달한 임의 헤더를 신뢰하지 않음. |
| S2~S8의 사용자 요청 → S1 | 현재 멤버십·권한 확인 | 초기 민감 요청은 온라인 검사. 허용 결과 캐시·회수 유예 시간은 미승인. |
| S3~S6 → S2 | 작업공간 상태·사용 설정 확인 | 정지·삭제 작업공간 신규 실행 거절. 조회 실패를 활성 상태로 취급하지 않음. |
| 자원 사용 서비스 → S7 | 사용권 확보·갱신·반환 | Q4 결정: 검사 장애 시 신규 실행 거절. 기존 사용권 만료 전까지만 실행하며 갱신 실패 시 안전하게 중단. |
| S6 → S4 | 외부 자료 수집 결과를 문서 리비전으로 저장 | 동일 수집 항목 키로 재시도. 문서 저장 확인 전 수집 커서 전진 금지. |
| S3 → S4/S6 | 권한 있는 문서·연결 작업 | 비밀 전달 대신 대상 서비스가 제한된 작업 수행. 무한 재시도 금지. |
| 각 서비스 → S8 | 추가 전용 감사 이벤트 전달 | Q5 결정: 중요 업무와 로컬 감사 Outbox를 함께 저장. 실패 시 업무 거절. 중앙 장애는 재전송·중복 제거로 대응. |

<a id="call-safety"></a>

<a id="순환-호출신뢰-경계-보강안"></a>

### 3.2. 순환 호출·신뢰 경계 보강안

- 업무 요청은 API/MCP에서 소유 서비스로 전달한다. S1은 신원·권한 검사 대상이지 모든 업무를 대신 전달하는 라우터가 아니다.

- 예: S3는 S2에 작업공간 상태를, S1에 권한을 확인한다. S2가 이를 처리하며 다시 S3를 호출하는 동기 순환은 금지하는 안이다.

- S1의 권한 검사는 S1이 소유한 할당만 판정한다. 요청자가 보낸 자원 정보 대신 소유 서비스가 확인한 정보를 사용한다.

- 신원 증명·대상 서비스·원래 요청자·행동·자원·요청 ID를 전달하는 내부 호출 계약을 정의한다. 구체 인증 기술은 미선정이다.

- S7·S8도 사용자 조회·설정 시 권한을 검사한다. 내부 계측·감사 수신은 인증된 생산자와 허용된 테넌트 범위를 검사한다.

- DB 트랜잭션을 연 채 원격 응답을 장시간 기다리지 않는다. 원격 검사 후 로컬 revision을 확인하고 충돌 시 재시도한다.

- 온라인 검사와 원격 부작용 사이 경합은 남는다. Q3은 전역 즉시 중단 보장이 아니라 안전 지점 중단이다.

<a id="트랜잭션실패-처리"></a>

## 4. 트랜잭션·실패 처리

| 업무 | 같이 확정할 데이터 | 분리 후 복구 |
| --- | --- | --- |
| 권한 회수 | S1 멤버십·권한 revision·변경 Outbox | 새 요청은 현재 권한 검사. 실행 중 작업은 안전 지점에서 재검사. 원격 동작의 즉시 중단을 보장한다고 가정하지 않음. |
| 작업공간 생성 | S2 생성 요청·소유 참조·준비 상태 | S1 기본 접근 할당을 멱등 요청. 준비 완료 전 접근 차단. 중단 후 동일 요청 키로 복구. |
| 에이전트 실행 | S3 Run·실행 Job·Outbox | 브로커 장애에도 요청 보존. 중복 전달은 claim·멱등 키로 제어. 허용량 확보 후 실패하면 반환·정합성 회수. |
| 작업 빌드·게시 | S2 빌드 요청·Outbox. 결과 수락과 릴리스 생성은 별도 트랜잭션. | 불변 소스·결과 해시·attempt 확인. 늦은 결과로 취소 상태를 덮어쓰지 않음. 게시·활성화는 구분. |
| 채팅 전송 | S5 메시지·변경 커서·Outbox | 클라이언트 요청 키로 중복 방지. 재연결은 저장된 이력으로 복구. 에이전트 자동 기동 없음. |
| 문서 업로드·수집 | S4 리비전·객체 참조·출처 | 객체 저장과 DB는 단일 트랜잭션이 아님. 응답 유실 시 리비전·해시 조회 후 판정. 불확실한 객체 즉시 삭제 금지 제안. |
| 한도 확보 | S7 원자적 사용권·중복 키 | 만료만으로 작업 종료를 추정하지 않음. 갱신 실패 시 중단·fencing 계약 필요. 단순 Redis 카운터가 영속 이력 전체를 대체하지 않음. |
| 작업공간 삭제 | S2 접근 정지·삭제 작업 상태 | 서비스별 정지·보존·삭제 확인을 추적. 실패한 단계만 재시도. 보존 기간·내보내기는 별도 사용자 결정. |

- **Outbox는 여러 DB의 변경을 하나의 원자적 트랜잭션으로 만들어 주지 않는다.**

- 서비스 간 업무는 준비·진행·완료·복구 필요 상태를 남긴다. 보상 불가능한 외부 동작은 수동 조정 경로가 필요하다.

- 전달 보장은 중복 가능한 재전송을 전제로 한다. 전체 시스템의 exactly-once 실행을 주장하지 않는다.

- 순서가 필요한 이벤트는 집합체별 revision으로 검증한다. 전체 서비스의 전역 순서는 가정하지 않는다.

| Q5: 로컬 감사 기록 저장 실패 | 중요 업무 변경까지 롤백. 성공 응답 금지. | 토큰 발급·권한 변경 등 중요 유스케이스의 트랜잭션 테스트. |

<a id="테넌트권한-경계"></a>

## 5. 테넌트·권한 경계

- S1은 신원·멤버십·할당 원본을 소유하고, 소유 서비스는 해당 자원의 행동 권한을 최종 집행한다.

- 서비스 신원과 원래 요청자 신원을 구분한다. 인증된 서비스라고 모든 테넌트 권한을 부여하지 않는다.

- MCP는 현재 사용자 권한과 토큰 범위의 교집합을 유지한다.

- 큐에는 불변 요청 식별자를 전달한다. 소유 서비스가 저장된 요청자·대상·현재 권한을 다시 확인한다.

- 서비스별 DB 역할과 테넌트별 RLS는 별개다. 둘 다 필요하다.

- DB 간 테넌트 ID 참조는 FK가 아니다. 소유 서비스가 발급한 ID와 로컬 참조 레코드를 구분한다. 로컬 FK·RLS와 온라인 권한 검사를 함께 적용하는 안을 검수한다.

- 개인 워크스페이스를 위해 사용자에게 조직·초대 기능을 노출하지 않는다. 내부 소유 표현은 7절 검수 대상이다.

- 전역 스케줄러에 모든 업무 DB의 BYPASSRLS 권한을 주지 않는다. 기존 예외를 바꾸려면 별도 정책 개정이 필요하다.

- 사용자 빌드에는 플랫폼 DB 계정·서비스 관리자 토큰을 전달하지 않는다.

- 스테이징·운영의 HTTPS·허용 출처·비밀 검증은 로컬 서버 배포에서도 유지한다.

## 6. DB·배포 대응

<a id="deploy-db"></a>

<a id="비교할-초기-db-구성"></a>

### 6.1. 비교할 초기 DB 구성

| 구성 | 장점 | 제약·판정 |
| --- | --- | --- |
| A. 같은 DB·서비스별 스키마 | 운영 단순. 초기 자원 비용 낮음. | 공유 DB 결합을 엄격히 통제해야 함. 서비스 독립성을 우선하는 이번 초안의 기본안은 아님. |
| B. 같은 PostgreSQL 인스턴스·서비스별 DB/역할 | 서비스 소유권과 독립 마이그레이션 분리. 로컬 배치 단순화. | **Q2 선택 완료**. 인스턴스 장애·CPU·I/O·물리 복구 시점 공유. FK·트랜잭션은 DB 간 연결 불가. |
| C. 서비스별 PostgreSQL 인스턴스 | DB 프로세스·설정·복구·자원 제한 분리 가능. | 메모리·연결·백업·운영 부담 증가. 같은 호스트라면 호스트 장애는 공유. |

- Q2에서 B를 선택했다. A/C는 비교 이력이다. 로컬 서버 사양·운영 예산을 확인하지 않아 용량 수치는 미정이다.

- 서비스별 DB는 사용자별 DB를 의미하지 않는다. 초기 테넌트 격리 모델은 별도다.

- Redis는 네임스페이스·ACL·용도별 연결을 분리한다. 큐·한도·캐시의 장애 영향이 크면 인스턴스도 분리한다.

- 객체 저장소는 문서·작업 산출물별 접근 주체와 테넌트 키를 구분한다. 고객 외부 DB 계정과 공유하지 않는다.

<a id="deploy-process"></a>

<a id="서비스-실행-단위"></a>

### 6.2. 서비스 실행 단위

- Q1에 따라 최종 확정된 서비스는 초기부터 독립 실행·배포한다. S1~S8이라는 후보 묶음 자체는 아직 미확정이다.

- API·MCP는 별도 진입점이다. 업무 서비스와 DB는 원칙적으로 외부에 직접 공개하지 않는다.

- `apps/jobs`의 실행 코드는 재사용할 수 있어도 모든 서비스의 작업자 권한을 한 프로세스에 합치지 않는다.

- 작업자는 소유 서비스별 큐·계정·허용 작업 목록으로 실행한다. Job 상태는 해당 업무 데이터 소유 서비스에 둔다.

- S3의 Run과 실행 Job은 같은 DB에 둔다. S2의 빌드 요청을 S3의 DB에 억지로 넣지 않는다.

- 빌드 샌드박스는 별도 신뢰 경계다. 제품 업무 서비스 8개라는 수에 격리 실행 환경 수가 포함되는 것은 아니다.

- 로컬도 dev·stg·prod의 DB·비밀·큐·객체 경로를 분리한다. 디렉터리만 나눠 같은 운영 계정을 쓰지 않는다.

- AWS 전환은 배치 대상 변경이다. ECS·EKS·EC2·RDS 등 구체 제품은 아직 선택하지 않는다.

- Docker·Makefile 재도입이나 특정 서비스 매니저 설치를 이 문서가 승인하지 않는다.

<a id="deploy-gates"></a>

<a id="운영복구-계약"></a>

### 6.3. 운영·복구 계약

- 서비스별 최대 DB 연결·큐 동시 실행·타임아웃·메모리·빌드 자원 상한을 배포 명세에 기록한다.

- readiness는 자기 필수 의존성을 검사한다. 모든 서비스 장애를 전 서비스 readiness 실패로 확산시키지 않는다.

- 릴리스는 구·신 계약 공존 후 소비자 전환, 마지막으로 구 계약 제거 순서로 진행한다.

- 마이그레이션은 서비스별 추가 방식이다. 기존 공유 Alembic 이력은 분리 전 대응표·이전 계획으로 보존한다.

- 백업은 서비스 DB·객체·이벤트 체크포인트를 함께 고려한다. DB 하나만 복구하면 서비스 간 참조가 어긋날 수 있다.

- Q6·Q7 결정: 초기 핵심 서비스 RTO 4시간 이내, RPO 최대 5분. 장애 범위·복구 절차·검증 기준은 후속 설계하며 고객 SLA로 주장하지 않는다.

- 확장 단위: API/MCP 요청량, S5 연결 수, S3 큐 대기 시간, S4 검색 부하, 격리 빌드 실행 수.

<a id="recovery-plan"></a>

<a id="rtorpo를-만족시키기-위한-설계-과제"></a>

### 6.4. RTO·RPO를 만족시키기 위한 설계 과제

- 제안 측정 기준: 장애 시작부터 핵심 읽기·쓰기가 복구될 때까지 RTO 측정. 감지·부재·준비·복원·검증 시간을 포함.

- RPO는 장애 직전 성공 응답한 업무와 복구 후 확인 가능한 마지막 업무 사이의 손실로 검증하는 안이다.

- DB 백업만이 아니라 문서 바이트·산출물·감사 대기 기록을 복구 가능한 동일 시점으로 맞춰야 한다.

- 공유 인스턴스 장애를 가정한 외부 백업 위치·변경 기록 보관·복원 호스트가 필요하다. 아직 선택·설치하지 않았다.

- 복구 시 소비자·스케줄러를 정지하고 DB·객체·이벤트 상태를 대조한 후 재생한다. 이전 토큰·사용권이 부활하지 않도록 epoch 변경·재검증안을 설계한다.

- 기존 DB 복구 시점보다 외부 제공자의 부작용이 앞설 수 있다. 중복 키·제공자 조회·수동 정합화 경로를 준비한다.

- 시간·손실 목표의 수치는 결정됐지만 장애 범위·측정 기준·도구·예비 자원은 후속 검수 대상이다.

## 7. 기존 명세와 충돌하는 부분

- **기존 문서의 규칙을 읽어 확인한 충돌**이다. 현재 코드 구현·DB 상태를 검증한 결과는 아니다.

| 기존 규칙·출처 | 문제 | 새 설계에서 할 일 |
| --- | --- | --- |
| [테넌트 FK·RLS](../../skills/rule-platform/SKILL.md#database) | 별도 DB는 S1/S2의 원본을 직접 FK로 참조할 수 없음. | 서비스별 로컬 테넌트 참조·검사·정지 전파 설계. 정책 수정 승인 전 분리 불가. |

<a id="디렉터리파일-명세-영향"></a>

## 8. 디렉터리·파일 명세 영향

- **현재 전체 트리를 수정하지 않았다.** 아래 항목은 서비스안 승인 후의 변경 대상이다.

- `apps/`: S1~S8 실행 진입점 배치 결정 필요. 앱 이름·하위 묶음은 서비스 확정 후 제안한다.

- `apps/api·mcp`: 서비스 클라이언트·인증 전달·오류 변환·조회 조합으로 책임 변경.

- `apps/jobs`: 소유 서비스별 실행 프로필·큐·권한. 기존 `jobs/jobs` 중첩도 파일 명세에서 재검토.

- `packages/core`: 서비스별 허용 도메인 의존성 목록 필요. 다른 서비스의 유스케이스 직접 import 금지.

- `packages/adapters`: 서비스별 DB 연결·저장소·원격 클라이언트 소유권 구분.

- `packages/contracts/schemas`: 생산 서비스·버전·호환성·생성기·py/ts 소비자를 기록.

- `migrations`: 서비스별 이력·기존 테이블 이전 대응. 기존 파일을 다시 쓰지 않는다.

- `tests`: 서비스 계약·테넌트 격리·실패 복구·호환성·서비스 간 통합 시나리오 추가.

- `deploy/local`·`env/local`: 환경별 서비스·DB·권한·비밀·복구 대응 추가.

- 기존 [파일 계획](../analyze-structure-file-plan/SKILL.md)·[이전 대응표](../process-structure-migration-ledger/SKILL.md)는 구형 목적지를 포함한다. 소스 경로는 보존하고 목적지만 재조정한다.

## 9. 사용자 결정과 검수 순서

| 결정 | 제안·대안 | 막히는 후속 작업 |
| --- | --- | --- |
| D1 서비스 경계 | 8개 후보를 기준으로 검수. S1 identity/organizations, S2 workspace/workbench는 우선 함께 유지 제안. | 서비스 실행 경로·소유 DB 확정. |
| D2 DB 분리 수준 | Q2 결정 완료: 인스턴스 공유·서비스별 DB/계정 분리. 물리 자원 수치는 후속. | 배포·백업·연결 풀·자원 수치. |
| D3 권한·사용량 장애 | Q3·Q4 결정 완료: 안전 지점 권한 재검사, 사용권 만료 전까지만 실행. | 취소·회수·정합성 시나리오. |
| D4 감사 정책 | Q5 결정 완료: 중요 업무와 로컬 감사 전달 기록 동시 저장. 실패 시 거절. | 기존 명세의 중요 업무 예외 반영·정확한 중요 작업 목록. |
| D5 제품 범위 | 커스텀 공유·게시 승인, 외부 DB 쓰기, 채팅 범위, 삭제 보존은 기능별 검수. | 해당 기능의 스키마·유스케이스 상세. |

- 선택한 DB 분리 수준을 기준으로 D1 서비스 묶음과 호출 계약을 검수한다.

- 도메인 간 호출·상태 전이·데이터 참조 규칙 확정.

- 7절 기존 명세 충돌을 한국어·영문 명세에 함께 정합화.

- 승인된 서비스 기준으로 목표 트리·파일 기록·이전 대응표 갱신.

- 단계별 구현 범위와 완료 조건 승인 후 솔로 구현.

- 다음 상세 설계 우선순위: S1 권한 → S2 작업공간 → S3 Run/Job → S7 사용권 → S8 감사의 계약 연결.

- 현재는 설계 초안 단계다. 제품 테스트는 사용자 지시대로 개편 후 단계로 보류했다.

- 이번 문서 점검은 링크·HTML 구조 확인이며 서비스·브라우저·운영 검증이 아니다.

<a id="조사-근거와-한계"></a>

## 10. 조사 근거와 한계

- 조사 확인일: 2026-09-15. 아래 일반 원칙을 우리 요구에 적용한 서비스 묶음은 작성자의 설계 제안이다.

- [Microsoft — 서비스 데이터 경계](https://learn.microsoft.com/en-us/azure/architecture/microservices/design/data-considerations): 물리 DB 서버 공유와 데이터 소유권 분리를 구분한다. 서비스 간 일관성과 복합 조회 비용을 지적한다.

- [AWS — 서비스별 DB](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-data-persistence/database-per-service.html): 독립 저장소·보안·확장 이점과 복합 트랜잭션·운영 비용을 설명한다.

- [AWS — Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html): DB 저장과 전달의 이중 쓰기 문제, 중복 소비와 멱등 처리를 설명한다.

- [OWASP — 권한 검사](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html): 모든 요청의 자원 권한 검사와 기본 거절 원칙을 제시한다.

- 현재 로컬 하드웨어·서비스 자원량·트래픽은 측정하지 않았다. 인터뷰에서 정한 복구 목표도 아직 달성 검증 전이다.

- SDK·브로커·서비스 매니저·샌드박스·AWS 제품은 이 문서에서 선정하지 않았다.
