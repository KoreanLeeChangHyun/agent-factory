# 외부 DB와 커스텀 작업 데이터 구조 조사

- 조사일: 2026-09-14 · 분류: 가공 자료(Processed) · 상태: 설계 검토안, 미승인

- 공식 문서에 대한 조사와 설계 제안이다. 특정 제품 도입·전체 파일 명세 확정·코드 변경·DB 연결·테스트·배포를 수행하지 않았다. 인용된 제품 문서는 해당 제품의 설명이지 우리 구현의 안전성을 입증하는 결과가 아니다.

- 기준: [제품 전체 그림](../../skills/design-platform/SKILL.md#product-overview) · [디렉터리 구조 계약](../../skills/rule-workbench-structure/SKILL.md#directory-contract). 이 문서는 채택 전 조사 자료이므로 AI용 규범 스킬로 승격하지 않는다.

<a id="사용자-요구와-이번-조사-범위"></a>

## 1. 사용자 요구와 이번 조사 범위

- 클라우드 에이전트 관제탑은 스탠다드 및 커스텀 작업, 선택적 사이드바와 패널 탭, 워크스페이스 MCP를 제공한다. 개인은 혼자 사용하며, 팀은 팀 플랜의 조직을 뜻한다. 별도의 조직 하위 팀 계층은 요구하지 않았다. 조직 소유자는 개별 권한으로 권한 집합을 구성해 사용자에게 부여한다. 커스텀 작업은 플랫폼이 컴파일·렌더링하며 외부 DB 연결이 필요하다.

- 이번 범위는 외부 DB 연결, 데이터 접근·권한·격리, 화면 바인딩, 버전·운영 안전성이다. 사용자 테이블 생성 기능, 커스텀 작성 언어, 지원 DB 전체 목록, 엔터프라이즈 보안 상품 구성은 미확정이다. 자료 조사 결과를 이런 결정의 승인으로 간주하지 않는다.

<a id="조사-결론"></a>

## 2. 조사 결론

- **설계 제안:** 연결 정보, 서버 데이터 작업, 작업 화면 정의를 분리한다. 화면과 MCP는 등록된 데이터 작업의 ID·버전·입력값을 전달하고, 서버가 현재 권한과 실행 정책을 확인한 뒤 외부 DB에 접근한다. 커스텀 작업 작성 언어와 무관하게 이 데이터 계약을 공유한다.

```text
사용자 또는 에이전트
  → 웹 API 또는 워크스페이스 MCP
  → 현재 신원·워크스페이스·권한·작업 버전 확인
  → 등록된 데이터 작업 + 검증된 입력값
  → 제한된 연결·DB 계정으로 실행
  → 반환 스키마·크기 제한·감사 메타데이터
  → 화면 바인딩 또는 MCP 결과

설정 저장소: 연결 메타데이터·권한·쿼리 버전·화면 정의
외부 DB: 고객 업무 데이터의 원본
비밀 저장소: 접속 자격증명
선택적 결과 저장소: 명시적으로 허용한 캐시·내보내기만
```

<a id="어떤-데이터를-어디에-둘-것인가"></a>

## 4. 어떤 데이터를 어디에 둘 것인가

| 데이터 종류 | 제안 소유 위치 | 주의점 |
| --- | --- | --- |
| 계정·조직·워크스페이스·권한 집합·할당 | 플랫폼 운영 DB | 외부 DB의 권한 설정과 별개인 관제 시스템의 기준 데이터 |
| 연결 정보 | 플랫폼 운영 DB의 메타데이터 + 분리된 비밀 참조 | 호스트·포트·DB 종류·연결 상태·소유 범위. 자격증명은 읽기 응답에 포함하지 않음 |
| 등록 쿼리·데이터 작업 | 플랫폼 운영 DB의 버전별 정의 | 쿼리 본문 자체에 비밀 상수가 들어갈 수 있어 편집·조회 권한과 로그 통제 필요 |
| 테이블·필드·관계 정보 | 제한된 스키마 메타데이터 스냅샷 | 열 이름도 민감할 수 있음. 실제 접속 계정이 열람할 수 있는 범위만 탐색 |
| 고객의 업무 레코드 | 외부 DB 원본 유지 | 연결 자체를 전체 데이터 복제나 마이그레이션으로 해석하지 않음 |
| 화면 정의·바인딩·릴리스 | 작업 정의 저장소 | 작업 참조와 입출력 계약만 포함. DB 비밀번호를 패키징하지 않음 |
| 실행 기록 | 플랫폼 감사·작업 이력 | 실행자·대상·버전·상태·시간·행 수 중심. 원문 결과·입력·비밀은 기본 기록 제외 |
| 캐시·내보내기 | 필요할 때만 별도 만료 정책을 가진 저장소 | 권한별 키·용량·보존 기간·권한 회수·삭제 처리를 먼저 설계 |

- 위 저장 분류는 우리 시스템에 대한 제안이다. DB 연결 지원이 내부 DB 생성이나 고객 데이터 영구 저장을 필수로 만들지는 않는다.

<a id="데이터-실행-방식-비교"></a>

## 5. 데이터 실행 방식 비교

| 방식 | 장점 | 부담 | 제안 |
| --- | --- | --- | --- |
| 화면·MCP가 임의 SQL 전달 | 자유로운 탐색 | SQL 작성자에게 접속 계정의 실질 권한이 노출됨. 행·열 정책, 함수·다중 구문·자원 소모 통제가 어려움 | 일반 작업 실행 경로에서는 제외. 향후 별도 관리자 도구로 검토 |
| 권한 있는 작성자가 쿼리를 등록·게시하고 ID로 실행 | 입출력·권한·버전·감사를 고정하기 쉬움 | 쿼리 작성과 게시도 고권한 행위로 다뤄야 함 | 초기 기본 후보 |
| 고객 API 또는 제한된 저장 프로시저 호출 | 기존 업무 규칙과 권한 경계를 활용 | 고객 개발 부담·API 수명 관리. 프로시저도 정의자 권한 등 별도 점검 필요 | 복잡하거나 민감한 쓰기 작업에 우선 검토 |
| 허용된 모델로 플랫폼이 CRUD 쿼리 생성 | 비개발자 접근성 | 타입·관계·DB 방언·복잡한 권한·동시성 설계가 늘어남 | 초기 계약 안정화 후 확장 후보 |

- 공식 근거: [Appsmith SQL 실행](https://docs.appsmith.com/connect-data/concepts/dynamic-binding-in-queries)은 동적 값 바인딩과 준비된 구문을 설명한다. [OWASP SQL 주입 방지](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)는 매개변수화·허용 목록·최소 권한을 권고한다. 값의 매개변수화가 테이블명·열명·SQL 구조까지 안전하게 만들어 주지는 않는다. 우리 설계에서는 동적 식별자를 서버 허용 목록으로 매핑하고, 미리 등록한 쿼리도 작성자·게시자 및 DB 권한 검토를 거치도록 제안한다.

<a id="권한-집합을-실제-데이터-권한에-연결하기"></a>

## 6. 권한 집합을 실제 데이터 권한에 연결하기

- **확정 요구:** 조직 소유자가 권한 집합을 구성하고 사용자에게 부여한다. **제안:** 연결 관리, 스키마 조회, 데이터 작업 편집·게시·실행·취소·내보내기를 구분한다. 권한 키와 범위 종류는 아직 최종 명세가 아니다.

```text
실행 허용 여부
  = 활성 사용자 및 워크스페이스 접근 가능
  AND 해당 범위의 데이터 작업 실행 권한
  AND 게시 버전과 연결 바인딩 사용 가능
  AND 데이터 제한 충족
  AND (MCP 호출이면 토큰 범위도 충족)
  AND 외부 DB 계정이 해당 SQL 실행을 허용
```

- 서버가 현재 세션·토큰에서 신원과 범위를 도출한다. 브라우저가 전달한 organization_id나 user_id를 그대로 권한 근거로 쓰지 않는다. 화면을 열 수 있다는 이유로 연결 관리·임의 조회 권한을 부여하지 않는다. 권한 집합 여러 개의 합산·거부 우선순위는 별도 결정이며 위 AND는 서로 다른 검증 경계에 대한 제안이다.

- 공유 DB 계정은 접속하는 모든 사용자를 같은 DB 사용자로 볼 수 있다. 플랫폼 권한 집합이 고객 DB의 행 접근 정책을 자동 생성하지 않는다. 초기에는 제한된 뷰·계정과 검토된 작업을 사용하고, 사용자별 DB 인증·고객 API·안전한 서버 컨텍스트 적용 중 필요한 방식을 정해야 한다. 신뢰하지 않는 SQL 작성자에게 임의 세션 컨텍스트 변경을 허용하면 컨텍스트 기반 행 제한도 우회될 수 있다.

- [PostgreSQL RLS 공식 문서](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)는 행 보안 정책과 함께 superuser·BYPASSRLS 및 일반적인 테이블 소유자의 우회를 설명한다. 따라서 RLS를 켰다는 사실만으로 테넌트 격리를 보장한다고 주장하지 않는다. 외부 DB마다 가능한 통제 수단도 다르다.

<a id="사설망-db-연결"></a>

## 7. 사설망 DB 연결

| 선택지 | 조건·영향 |
| --- | --- |
| TLS 직접 연결 + 고정 송신 IP 허용 | 고객 DB에 접근 가능한 경로가 필요. 단순하지만 DB를 인터넷에 개방하도록 강제해서는 안 됨 |
| SSH bastion 경유 | DB 자체를 공개하지 않고 접근. bastion 도달성·호스트 키 검증·키 회전·터널 제한 필요 |
| 전용망·VPN 등 | 네트워크 운영 비용과 대상별 설정 증가. 고객 요구와 배포 조건을 보고 선택 |
| 고객 망 내부 커넥터가 외부로 연결 | 인바운드 개방을 줄일 수 있는 설계 후보. 별도 실행기·배포·등록·폐기·업데이트 계약이 필요하며 현재 기능으로 가정하지 않음 |

- SSH 방식의 제품 사례는 [Retool 공식 문서](https://docs.retool.com/data-sources/guides/connections/ssh-tunnels)에서 확인했다. 나머지는 우리 시스템에 적용할 네트워크 설계 대안이며 이번 조사에서 제품별 구현 비교나 연결 실험을 하지 않았다.

- [OWASP SSRF 방지](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)의 목적지 허용 목록·DNS 검증 원칙을 참고하되, DB 연결에 대한 적용은 설계 해석이다. 사용자 지정 호스트·포트로 플랫폼 내부 DB나 메타데이터 서비스에 접속할 수 없어야 한다. 공용 연결과 승인된 사설망 경로를 분리하고, 목적지·포트·DNS 재해석·터널 포워딩·DB별 리다이렉트 기능을 통제한다. 사설 IP를 무조건 허용하거나 전부 차단하는 단일 규칙으로 처리하지 않는다.

<a id="화면-바인딩과-버전-계약"></a>

## 8. 화면 바인딩과 버전 계약

- 제안 데이터 작업 레코드: ID, 소유 범위, 연결 바인딩, 버전, 읽기/쓰기 종류, 입력 스키마, 출력 스키마, 실행 정책, 요구 권한. 제안 화면 바인딩: 데이터 작업 ID·버전, 입력 매핑, 결과 매핑, 갱신 조건. 브라우저에는 실행 가능한 최소 계약만 제공한다.

```text
작업 화면: 주문 관제
  # 예시이며 실제 기능으로 확정한 것이 아님
목록 바인딩 → orders.list@v1
입력        → 상태·페이지 커서
서버 입력   → 현재 사용자·워크스페이스 (사용자 수정 불가)
출력        → 행 목록·열 타입·다음 커서·조회 시각
화면 상태   → 로딩·빈 결과·오류·권한 없음·갱신 중
```

- 페이지 이동·필터·정렬은 서버 실행 계약에 포함하고 페이지 크기와 정렬 키를 제한한다. 기본은 수동 갱신 또는 제한된 주기 조회로 시작하는 안이다. 구독·CDC는 별도 운영 기능으로 두며 외부 DB가 바뀌면 자동 실시간 반영된다고 약속하지 않는다.

- 조회 결과 타입은 큰 정수·정밀 소수·시간대·바이너리·NULL 표현까지 정의해야 한다. 출력 스키마 변경을 감지하면 진단을 표시하고 호환되지 않는 작업은 실행을 제한하는 정책을 정한다. 스키마 스냅샷은 변경 탐지 보조이며 완전한 호환성 증명은 아니다. 게시된 작업 버전은 연결 계정·테이블명을 브라우저에서 임의 교체하지 못하게 한다.

- 커스텀 화면이 JavaScript/TypeScript를 사용하더라도 DB 비밀은 런타임에 주입하지 않는다. 데이터 SDK 또는 제한된 메시지 인터페이스만 제공하는 방향이다. 구체적 컴파일·샌드박스는 이번 조사 범위 밖이며 언어 선택을 확정하지 않는다.

<a id="운영-안전성과-쓰기-실패"></a>

## 9. 운영 안전성과 쓰기 실패

- 플랫폼 운영 DB 연결 풀과 고객 외부 DB 풀을 분리한다. 외부 풀은 소유 범위·연결·자격증명 리비전별로 구분하고 전체/고객별 연결 상한과 유휴 회수를 둔다.

- 연결·쿼리·잠금 대기·전체 실행에 제한을 두고 결과 행 수·바이트·페이지 크기를 제한한다. 브라우저에서 결과를 잘라도 DB 연산 비용이 제한되는 것은 아니다.

- 읽기 전용 여부는 SQL 첫 단어 검사만으로 판단하지 않는다. DB 계정 권한과 트랜잭션 제한, 허용 작업 정의를 함께 사용한다.

- 캐시는 초기 기본값을 비활성으로 제안한다. 도입 시 범위·신원/권한·작업 버전·입력·연결 리비전을 키에 반영하고 조회 시 재인가한다.

- AI가 만든 SQL도 신뢰하지 않는 입력이다. 일반 MCP 실행에서는 등록 작업만 호출하도록 제안하며 쿼리 작성·게시를 별도 권한으로 둔다. 조회 결과가 AI로 전달되는 범위도 별도 통제한다.

- 외부 쓰기와 플랫폼 실행 이력 사이에는 일반적으로 하나의 로컬 트랜잭션이 없다. 외부 커밋 뒤 연결이 끊기면 결과를 알 수 없을 수 있다. 자동 재시도는 중복 쓰기를 만들 수 있으므로 외부 측 멱등성 키·조건부 변경 또는 결과 대조가 있어야 한다.

- 결과 불명 상태를 단순 실패로 바꾸지 않는다. 취소 요청도 이미 커밋된 외부 변경을 되돌린다는 뜻이 아니다. 승인 기능 도입 여부와 위험 작업의 사용자 확인 조건은 후속 결정이다.

- 공식 근거: [PostgreSQL 실행 제한](https://www.postgresql.org/docs/current/runtime-config-client.html)은 statement_timeout·lock_timeout·트랜잭션 관련 설정을 설명한다. [SQLAlchemy 연결 풀](https://docs.sqlalchemy.org/en/20/core/pooling.html)은 반환 시 rollback만으로 모든 세션 자원이 초기화되지 않을 수 있음을 설명한다. 풀 분리·재시도·결과 불명 처리 정책은 이를 고려한 우리 설계 제안이다. DB별 취소·세션 초기화 동작은 별도 검증이 필요하다.

<a id="도메인-및-파일-책임-후보"></a>

## 10. 도메인 및 파일 책임 후보

- 아래는 이번 데이터 조사로 도출한 배치 후보다. 새로운 루트나 구현 파일을 생성하지 않는다. 전체 트리·파일별 함수·입출력·이전 대응표까지 확정된 상태는 아니다. 데이터 작업 도메인의 명칭과 기존 connections 도메인과의 경계도 검수 대상이다.

```text
packages/core/
├── connections/                   # 연결 소유·상태·자격증명 교체의 공통 업무 규칙
├── identity/                      # 사용자 신원·실행 권한 판정
├── organizations/                 # 조직 권한 집합과 사용자 할당
├── data_access/                   # 제안: 외부 데이터 작업 도메인
│   ├── domain.py                  # 연결 참조·작업 정의·버전·실행 상태
│   ├── ports.py                   # 외부 실행·스키마 조회·정의 저장 인터페이스
│   ├── policies.py                # 입력·작업 범위·실행 한도·쓰기 정책
│   └── use_cases.py               # 작업 등록·게시·실행·취소 흐름
└── workbenches/                   # 작업 릴리스와 데이터 작업 참조 검증

packages/adapters/
├── postgres/                      # 플랫폼 운영 데이터 저장. 고객 SQL 실행과 구분
└── external_db/                   # 제안: 고객 DB 접근 구현
    ├── postgres.py                # PostgreSQL 외부 접속·실행·메타데이터 조회
    ├── pools.py                   # 격리된 연결 풀·회수·자격증명 변경 처리
    └── network.py                 # 허용 목적지·TLS·네트워크 경로 검증

apps/api/
├── routes/data_access.py          # 웹의 데이터 작업 관리·실행 입출력
└── services/data_access.py        # HTTP 실행 흐름·세션과 패키지 의존성 조립
apps/mcp/
├── tools/data_access.py           # 허용된 데이터 작업의 MCP 입출력
└── services/data_access.py        # MCP 인증 범위와 공통 유스케이스 연결
apps/worker/jobs/data_access.py    # 장기 실행·내보내기 도입 시 처리
apps/web/
├── pages/db/                      # DB 작업 화면: 연결·스키마·작업 정의
└── api/data-access.ts             # 웹 HTTP 클라이언트. SQL·비밀 처리 금지
packages/workbench-runtime/
└── bindings.ts                    # 데이터 계약의 화면 바인딩. DB 드라이버 금지
contracts/schemas/data-access/v1/  # 제안: 입력·출력·작업 참조 스키마
```

- 신규 데이터 기능 테스트는 tests/api·mcp·worker 및 tests/packages/core/data_access와 tests/packages/adapters/external_db 등 소유자 기준 후보에 대응한다. 테스트는 설계만 하며 실행하지 않는다. 연결 UI를 연동 작업과 DB 작업 양쪽에서 보여주더라도 연결 저장·권한 규칙을 두 벌로 구현하지 않는다.

<a id="기존-명세와-조정이-필요한-부분"></a>

## 11. 기존 명세와 조정이 필요한 부분

- 로컬 authorization.md에는 팀 멤버십과 기존 역할 합산 규칙이 남아 있다. 최근 사용자는 팀이 곧 팀 플랜의 조직이라고 설명했으므로 별도 하위 팀 모델을 이번 설계에서 가정하지 않는다. 기존 규칙은 구조·권한 명세 갱신 시 대조해야 한다. integrations.md의 연결당 단일 워크스페이스 소유 규칙을 따르면 초기 바인딩도 워크스페이스로 제한하는 안이 일관적이다. 조직 전체 연결 공유는 아직 승인되지 않았다.

- database.md의 PostgreSQL 기준은 플랫폼의 기준 DB에 대한 규칙으로 유지하면서, 외부 연결 지원 범위를 별도 명세해야 한다. 외부 DB 지원이 플랫폼 DB 교체를 뜻하지 않는다. 보안 문서의 HTTP 외부 URL 규칙을 DB 프로토콜에 그대로 적용하지 말고 프로토콜별 경계를 정해야 한다. 이 조사에서는 기존 규범 문서를 자동 변경하지 않았다.

<a id="초기-도입-제안과-결정-목록"></a>

## 12. 초기 도입 제안과 결정 목록

- **초기 후보:** PostgreSQL 한 종류의 외부 연결 + 최소 권한 읽기 계정 + 등록·게시된 매개변수 쿼리 + 페이지 단위 결과 + 웹/MCP 공통 인가 + 감사 메타데이터. PostgreSQL 우선은 기존 플랫폼 기반을 활용하려는 제안이며 사용자의 고객 DB 수요를 조사한 결과가 아니다. MySQL·SQL Server 등은 실제 요구와 드라이버 검증 후 확장한다.

- 초기에 제한할 후보: 일반 사용자 임의 SQL, 테이블 생성·삭제, 자동 전체 복제, 범용 SQL 재작성형 행 보안, 무제한 결과 캐시. 쓰기 지원이 초기 필수라면 제한된 명령/API와 결과 불명·멱등성 처리를 초기 범위에 추가해야 한다.

- 첫 연결 대상 DB와 버전은 무엇인가?

- 고객 데이터가 공용 접근 가능한가, 사설망에 있는가? 초기 지원 경로는 무엇인가?

- 초기는 조회만 필요한가, 변경도 필수인가?

- 연결·쿼리를 만들고 게시할 수 있는 사람은 누구인가?

- 같은 워크스페이스 사용자 간에도 행·열 접근 제한이 필요한가?

- 연결 소유는 워크스페이스 단위로 시작할 것인가? 조직 공유가 필요한가?

- 외부 데이터의 캐시·내보내기·AI 전송을 어디까지 허용할 것인가?

- 다음 설계 순서: 위 결정 → 연결·데이터 작업·바인딩·권한 계약 → 디렉터리 책임 확정 → 파일별 입출력·주요 심볼·실패 처리·검수 시나리오 → 사용자 검수. 아직 커스텀 작업 전체 컴파일·렌더링 구조나 전체 저장소 파일 명세가 완료된 것은 아니다.

<a id="후속-검수-시나리오"></a>

## 13. 후속 검수 시나리오

- 타 조직 연결 ID 변조, 개인의 타 사용자 연결 접근, 실행 직전 권한 회수, MCP 토큰 범위 초과, 매개변수 주입, 동적 식별자 변조, 위험 목적지·DNS 변경, 결과 상한 초과, 장기 잠금, 풀 간 신원 오염, 자격증명 회전, 게시 후 스키마 변경, 커밋 후 통신 단절, 중복 실행, 캐시의 타 사용자 결과 노출을 포함한다. 실제 검증 실행은 합의한 후속 테스트 단계에 수행한다.
